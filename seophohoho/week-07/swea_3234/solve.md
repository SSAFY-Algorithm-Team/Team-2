# SWEA 3234 - 준환이의 양팔저울

## 1. 뭘 세라는 거지

추 N개를 하나씩 저울에 올린다. 두 가지를 동시에 정한다.

- **순서**: 어떤 추를 몇 번째로 올릴지 → N!
- **방향**: 각 추를 왼쪽에 올릴지 오른쪽에 올릴지 → 2^N

합쳐서 2^N · N! 가지. 여기서 **중간 과정 내내** "오른쪽 합 ≤ 왼쪽 합"을 지킨 경우만 센다.

중요한 건 "중간 과정 내내"다. 마지막에만 맞으면 되는 게 아니라, 추를 올릴 때마다 매번 성립해야 한다. 그래서 단순 조합 공식이 안 나온다. 올리는 순서가 답에 영향을 준다.

추 무게가 서로 다르다는 조건도 눈여겨봤다. 중복 순열 보정을 안 해도 된다는 뜻이다.

## 2. 완전탐색 규모부터 재보기

N ≤ 9니까 최악은 2^9 · 9! = 512 · 362,880 ≈ **1억 8천만**.

파이썬으로 1억 8천만 개를 하나씩 돌리는 건 당연히 안 된다. 그런데 더 나쁜 신호가 있었다. **샘플 3번의 답이 35,583,723**이다. 답 자체가 3천만이다.

이게 왜 나쁜 신호냐면, 유효한 경우를 리프(leaf) 하나씩 세는 DFS는 _정답 개수만큼_ 함수 호출을 해야 한다. 가지치기로 무효한 가지를 아무리 잘라도 3천만 번은 무조건 내려간다는 뜻이다.

> 리프(leaf) — 재귀 트리의 맨 끝, 추를 다 올려서 더 내려갈 데가 없는 지점.

**결론: "무효한 가지를 자르는" 가지치기만으로는 부족하다. 유효한 가지도 통째로 접어야 한다.**

## 3. 상태를 뭘로 잡을까

순서를 고르는 문제니까 순열 DFS다. "어떤 추를 이미 썼는지"를 들고 다녀야 한다.

N ≤ 9라서 비트마스크(bitmask)를 썼다. 방문 배열 대신 정수 하나로 끝난다.

> 비트마스크(bitmask) — 켜짐/꺼짐 9칸을 정수 하나의 2진수 자릿수로 표현하는 것.

여기에 왼쪽 합, 오른쪽 합을 같이 들고 다니면 상태가 완성된다.

```
dfs(used, left, right, remain_sum, remain_cnt)
```

`remain_sum`(남은 추 무게 총합)과 `remain_cnt`(남은 추 개수)는 `used`에서 매번 다시 계산할 수도 있지만, 어차피 가지치기에 쓸 거라 인자로 들고 내려가게 했다.

## 4. 가지치기 1 - 애초에 위반할 가지는 만들지 않는다

가장 먼저 떠오른 건 당연한 거였다.

- **왼쪽에 올리기**: 왼쪽만 커지니까 조건이 깨질 수 없다. 항상 허용.
- **오른쪽에 올리기**: `right + w ≤ left`일 때만 허용.

```python
count += dfs(nxt, left + w, right, ...)
if left >= right + w:
    count += dfs(nxt, left, right + w, ...)
```

"일단 내려간 다음 틀렸으면 0 리턴"이 아니라, **조건을 만족할 때만 재귀 호출 자체를 만든다.** 무효한 서브트리는 아예 태어나지 않는다.

이건 정확성엔 필수지만, 2절에서 봤듯 속도 문제는 이걸로 안 풀린다.

## 5. 가지치기 2 - 여기가 핵심

3천만 개 리프를 하나씩 세면 안 된다면, **"여기서부터는 뭘 해도 다 정답"인 지점을 찾아서 공식으로 한 방에 세야 한다.**

그 지점이 언제인가?

오른쪽 접시는 추를 올릴수록 **커지기만 한다**. 왼쪽도 마찬가지다. 그런데 최악의 경우를 생각해보면 — **남은 추를 전부 오른쪽에 몰아넣어도** 오른쪽이 왼쪽을 못 넘는 상황이 있다.

```
left >= right + remain_sum
```

이 조건이 성립하면:

- 오른쪽 합의 **최종 상한**이 `right + remain_sum`인데 그게 이미 `left` 이하다.
- 오른쪽은 단조증가(monotonic)라서 중간 어느 시점의 오른쪽 합도 그 상한보다 작다.
- 왼쪽은 줄어들지 않는다.

즉 **중간 과정 전부 자동으로 안전하다.** 남은 추를 어떤 순서로, 어느 쪽에 올리든 다 정답이다.

> 단조증가(monotonic) — 한 방향으로만 변하고 되돌아가지 않는 것.

그럼 남은 경우의 수는 제약 없는 전체 개수 그대로다.

```python
return math.factorial(remain_cnt) * (1 << remain_cnt)
```

`remain_cnt!` (순서) × `2^remain_cnt` (좌우 선택). `1 << remain_cnt`는 2의 거듭제곱을 비트 시프트로 쓴 것이다.

**이 한 줄이 수백만 개 리프를 한 번의 곱셈으로 접는다.** 3천만 개를 세면서도 실제 함수 호출은 그것보다 훨씬 적어진다.

## 7. 막다른 길 - "집합 고르고 팩토리얼 곱하기"

풀다 보면 이런 접근이 떠오른다.

1. 전부 왼쪽에 몰빵하는 경우 N!을 먼저 더한다.
2. 오른쪽에 올릴 추들을 집합으로 고른다.
3. 그 집합의 합이 나머지 합보다 작으면 통과시키고, 순서 경우의 수(팩토리얼)를 곱해서 더한다.

조합 공식으로 한 방에 끝나니까 매력적이다. **그런데 틀린다.**

### 왜 틀리나 - 지문을 다시 본다

지문에 두 번 못박혀 있다.

- 제약 설명: **"무게 추를 올릴 때"** 오른쪽이 왼쪽보다 커지면 안 된다
- 출력 조건: **"무게추를 올리는 과정에서"** 커지지 않는 경우의 수

다 올린 뒤가 아니라 **올리는 시점마다**다. '과정에서'가 핵심 단어다.

### 샘플이 직접 증명한다

무게 1, 2, 4에서 **최종 합만** 따진다고 치고 세보자.

`합(S) ≤ 합(나머지)`인 오른쪽 집합: `{}`, `{1}`, `{2}`, `{1,2}` → 4개.
순서가 상관없다면 각각 3! = 6.

**4 × 6 = 24.**

그런데 정답은 **15**다. 지문 그림에 15개를 다 그려놨다. 24 ≠ 15이므로 최종 합 해석은 그 자리에서 반박된다.

### 깨지는 정확한 지점

팩토리얼을 곱한다는 건 **"이 집합이 통과했으니 순서는 아무거나 다 된다"**고 선언하는 것이다. 순서가 결과를 바꾸지 않아야 성립한다.

S = {1}로 고정하고 6가지 순서를 다 펼쳐보면:

| 순서                  | 진행            | 결과           |
| --------------------- | --------------- | -------------- |
| 1(우) → 2(좌) → 4(좌) | 왼0 / 오1       | 첫 수에서 탈락 |
| 1(우) → 4(좌) → 2(좌) | 왼0 / 오1       | 첫 수에서 탈락 |
| 2(좌) → 1(우) → 4(좌) | 왼2 → 오1 → 왼6 | 통과           |
| 2(좌) → 4(좌) → 1(우) | 왼2 → 왼6 → 오1 | 통과           |
| 4(좌) → 1(우) → 2(좌) | 왼4 → 오1 → 왼6 | 통과           |
| 4(좌) → 2(좌) → 1(우) | 왼4 → 왼6 → 오1 | 통과           |

같은 집합인데 6개 중 4개만 산다. 이 방식은 여기서 6을 더한다. 2를 더 센다.

**집합은 순서를 기억하지 못한다.** 그게 깨지는 지점이다.

### 집합별 실제 생존 수 (정답 15의 내역)

| 오른쪽 집합 | 합 비교 | 유효한 순서 수 |
| ----------- | ------- | -------------- |
| {}          | 0 ≤ 7   | 6 = 3!         |
| {1}         | 1 ≤ 6   | **4**          |
| {2}         | 2 ≤ 5   | **3**          |
| {1,2}       | 3 ≤ 4   | **2**          |
| 나머지      | 탈락    | 0              |

6 + 4 + 3 + 2 = 15.

4, 3, 2다. 상수가 아니다. 3!도 2!도 아니고 집합마다 제각각이다. 어떤 상수를 곱해도 안 맞는다.

### 그래도 맞은 부분 - 그리고 그게 핵심이다

"전부 왼쪽 = N!"은 맞다. 위 표의 첫 행이 그거다.

왜 그건 맞나? **오른쪽이 영원히 0이라 순서가 무의미해지기 때문이다.** 순서가 무의미해진 순간에만 팩토리얼을 쓸 수 있다.

5절의 가지치기가 정확히 그 조건의 일반화다. `left >= right + remain_sum`은 "지금부터는 뭘 어떻게 올려도 안 터진다" = "여기서부터 순서가 무의미하다"는 선언이다. 그 지점에서만 `cnt! × 2^cnt`로 접는다.

이 접근이 틀린 이유는 그 선언을 **처음부터** 해버린 것이다. 시작 시점엔 아직 순서가 무의미하지 않다.

### 남는 결론

집합 단위로 쪼개는 방향 자체는 살릴 수 있다. 다만 집합마다 "유효한 순서 수"를 따로 세야 하는데, 그걸 세는 게 결국 원래 문제와 같은 난이도다.

이건 **접두사 제약(prefix constraint)** 문제다.

> 접두사 제약(prefix constraint) — 수열을 앞에서부터 잘라 본 모든 토막이 각각 조건을 만족해야 하는 것.

최종 상태만 보는 조합 공식으로는 닫히지 않는다. 그래서 DFS로 과정을 실제로 밟아야 한다.

## 8. 그런데 시간이 안 맞는다

여기서 멈추지 않고 최악 입력을 만들어 재봤다. N=9짜리 21개 테스트케이스.

```
53.43s
```

**제한이 4초인데 53초.** C/C++면 통과하는 풀이지만 파이썬으로는 TLE다.

케이스 하나에 약 2.5초. 5절 가지치기가 있는데도 이렇다. 왜냐면 가지치기가 발동하려면 왼쪽이 충분히 무거워져야 하는데, 트리 **위쪽**(추를 몇 개 안 올린 상태)에서는 그 조건이 거의 안 걸린다. 위쪽 폭은 그대로 다 펼쳐진다.

## 9. 한 걸음 더 - 상태가 중복된다

다시 상태를 봤다.

```
dfs(used, left, right, remain_sum, remain_cnt)
```

인자가 5개지만 **독립적인 건 2개뿐이다.**

- `remain_cnt` = N − (used의 켜진 비트 수) → `used`로 결정됨
- `remain_sum` = 전체합 − (used에 속한 추들의 합) → `used`로 결정됨
- `left` = (used에 속한 추들의 합) − `right` → **`used`와 `right`로 결정됨**

즉 진짜 상태는 `(used, right)` 둘뿐이다. 나머지는 전부 파생값이다.

그러면 **서로 다른 경로로 같은 `(used, right)`에 도달하는 경우가 잔뜩 생긴다.** 예를 들어 추 3, 5를 "3→왼쪽, 5→오른쪽" 순으로 올린 것과 "5→오른쪽, 3→왼쪽" 순으로 올린 것은 도착 상태가 완전히 같다. 앞으로 셀 경우의 수도 같다. 그런데 지금 코드는 매번 처음부터 다시 센다.

이게 중복 부분문제(overlapping subproblems) — 메모이제이션(memoization)이 먹히는 전형적 신호다.

> 메모이제이션(memoization) — 같은 입력으로 부른 함수 결과를 저장해두고 재활용하는 것.

`@lru_cache`를 얹고 `left`를 인자에서 빼서 `used`로부터 계산하게 바꿨다.

```
0.22s
```

**53초 → 0.22초. 약 240배.** 21개 케이스 전부에서 답도 동일했다.

## 10. 정리

| 단계       | 아이디어                                      | 효과                                    |
| ---------- | --------------------------------------------- | --------------------------------------- |
| 상태       | 비트마스크 순열 DFS                           | 방문 관리 O(1)                          |
| 가지치기 1 | 오른쪽 올릴 때 조건 검사 후 호출              | 무효 서브트리 제거                      |
| 가지치기 2 | `left >= right + remain_sum` → `cnt! · 2^cnt` | **유효 서브트리를 곱셈 한 번으로 접음** |
| 버린 길    | 집합 고르고 팩토리얼 곱하기                   | 순서를 못 세서 오답 (24 vs 15)          |
| 최적화     | `(used, right)`로 메모이제이션                | 53s → 0.22s                             |

핵심 한 줄로 말하면, 이 문제는 **"세는 문제인데 답이 3천만이라, 리프를 세지 말고 서브트리를 닫힌 형태(closed form)로 접어야 하는"** 문제다. 그리고 상태 공간을 다시 들여다보면 `left`가 종속 변수라는 걸 알아채는 순간 메모이제이션이 열린다.

현재 `solve.py`는 8절 최적화가 빠진 버전이라, 파이썬 제출 기준으로는 메모이제이션을 얹어야 안전하다.
